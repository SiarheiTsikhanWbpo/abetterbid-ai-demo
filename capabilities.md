# AI-поддержка: что умеет решение и какие данные нужны для демо A Better Bid

## Что это за продукт

AI-помощник клиентской поддержки: принимает вопрос голосом или в сообщениях, использует информацию компании и данные из подключённой системы, отвечает в рамках заданных правил и при необходимости подключает сотрудника.

Исходный проект создан для туроператора с интеграцией с Tourman. Ниже описаны возможности нашего AI-решения по текущему коду. Это не описание всех функций сайта Tourman и не подтверждение уже работающей интеграции с A Better Bid.

## Что реализовано в исходном решении

| Возможность | Что делает | От чего зависит |
|---|---|---|
| Голосовой разговор | Принимает телефонный звонок, распознаёт речь, формирует ответ и озвучивает его; обрабатывает перебивания и паузы | Подключённая телефония, речевые движки и настройки |
| Текстовые обращения | Есть обработка WhatsApp-сообщений и SMS, адаптеры получения и отправки | Аккаунты каналов, разрешения и конфигурация |
| Поиск клиента | Находит клиента по доступному идентификатору: телефону, email или коду брони | Что поддерживает конкретный источник; правила идентификации |
| Чтение данных | Получает бронь, карточку тура, выезды и расписание; отвечает по возвращённым данным | Доступность полей и методов API |
| FAQ и инструкции | Использует бизнес-контекст компании и правила ответа; сообщает, если информации недостаточно | Утверждённые материалы и актуальность источников |
| Передача сотруднику | Поддерживает перевод звонка по заданным правилам, с учётом доступности и часов операторов | Настроенный маршрут и реальный ответ сотрудника |
| Итог разговора | Формирует краткое содержание, результат, неотвеченные вопросы и историю для контакт-центра | Подключение Chatwoot; запись заметки в исходную систему — только если её API это поддерживает |
| Дополнительное сообщение | Есть сценарии отправки деталей, например точки встречи или контакта гида | Разрешённые данные, подходящий канал и результат отправки |
| Неудачный перевод | Есть механизм заявки на обратный звонок через SMS сотруднику | Подключённая SMS-отправка; заявка не гарантирует, что сотрудник перезвонит |
| Напоминания | Есть планировщик событийных контактов, повторов и переходов между каналами | Сейчас события туристические; для A Better Bid нужны собственные правила |

Возможности источников различаются. Например, если подключённый API не умеет записывать заметки или не возвращает нужное поле, помощник не должен изображать успешное действие.

Жёсткие правила текущего агента привязаны к прежнему заказчику. Для нового бизнеса требуется адаптировать их вместе с инструментами и источниками данных.

### Языки и каналы

- В текущем коде рабочего голоса предусмотрены английский и испанский. Русский голос для реальных звонков потребуется отдельно подключить и проверить.
- Русский интерфейс и подготовленные русские диалоги уже есть в презентационном демо. Опциональная озвучка браузера не является голосовым движком рабочего сервиса.
- WhatsApp-звонки нельзя считать готовым каналом: медиапуть и живой прогон требуют отдельной проверки. Текстовый WhatsApp и звонок на телефонный номер — разные интеграции.
- Наличие реализации в коде не означает, что все каналы подключены и проверены у нового заказчика.

## Что сейчас умеет демо для A Better Bid

Есть пять экранов: обзор, диалоги, AI-помощник, аналитика и база знаний. Работают переключение сценариев и каналов предпросмотра, воспроизведение подготовленного диалога, поиск, фильтры, карточки обращений, экспорт примеров и предпросмотр передачи сотруднику.

Подготовлены три темы:

1. **Допуск к торгам:** покупатель не понимает, какой шаг регистрации остался; агент объясняет следующий шаг и направляет к официальной инструкции.
2. **Доставка:** покупатель спрашивает о статусе, стоимости и получении авто; агент различает известный статус и информацию, которую должна подтвердить команда.
3. **Документы:** покупатель спрашивает об обработке и отслеживании; агент объясняет порядок и не обещает дату без подтверждения.

Ссылки на публичные правила взяты из [официального центра помощи A Better Bid](https://help.abetter.bid/hc/user-guide/en). Реплики заранее подготовлены. Профили, лоты, статусы и показатели вымышлены; закрытый API и рабочий AI-оркестратор к этому интерфейсу пока не подключены.

## Какие примеры данных нужны от A Better Bid

Для первого содержательного демо достаточно одного-двух процессов. Предлагаем начать с регистрации и доставки; окончательный выбор — по вашим частым обращениям.

### Минимальная выгрузка

| Что прислать | Объём для начала | Что должно быть внутри |
|---|---|---|
| Типичные обращения | 15–30 обезличенных переписок; при наличии 5–10 расшифровок звонков | Вопросы клиента, уточнения сотрудника, ответы и итог |
| Правильное поведение | Для каждого примера | Какой ответ ожидается, что можно сообщить и какое действие разрешено |
| Связанные объекты | 5–10 наборов | Демо-клиент, профиль, лот, доставка или документы; связи между объектами должны сохраняться |
| Словарь статусов | Для выбранного процесса | Код, значение для клиента, допустимый следующий шаг и случаи передачи специалисту |
| FAQ и правила | Актуальная версия | Условия, ограничения, исключения и источник, который считается главным |
| Идентификация | Краткое описание | Как подтверждается клиент; какие данные доступны до проверки и после неё |
| Передача сотруднику | Несколько примеров | Причина, нужная команда, часы работы, обязательные поля и действия при недоступности |

Особенно полезны примеры, где данных нет, системы противоречат друг другу, статус устарел, клиент просит человека или задаёт вопрос о другом лоте. Для таких случаев тоже нужен ожидаемый ответ.

### Формат одного примера

Можно прислать JSON, CSV, XLSX или обычный документ. Собственный экспорт подходит; заранее переделывать его под нашу схему не обязательно.

Условный пример ниже — это формат для обсуждения, а не описание существующего API A Better Bid:

```json
{
  "example_id": "demo-case-01",
  "customer_ref": "demo-customer-01",
  "customer_message": "Что с доставкой моего автомобиля?",
  "lot_ref": "demo-lot-01",
  "access_to_this_lot_confirmed_in_example": true,
  "available_data": {
    "shipping_status": "awaiting_carrier",
    "shipping_status_meaning": "Заявка принята, перевозчик не назначен",
    "confirmed_delivery_at": null,
    "updated_at": "2026-10-15T08:00:00Z"
  },
  "expected_answer": "Заявка принята, перевозчик пока не назначен. Подтверждённой даты доставки нет.",
  "handoff_required": false,
  "forbidden_promises": ["Называть точную дату доставки без подтверждения"]
}
```

Признак доступа в примере обозначает результат вашей согласованной проверки. Само знание номера лота не должно автоматически давать доступ к приватным данным.

### Что сохранить при обезличивании

- Заменить имена, телефоны, email и идентификаторы на вымышленные; одинаковый клиент и лот должны оставаться связанными во всех файлах.
- Сохранить последовательность реплик, статусы, исключения, связи и временные интервалы, необходимые для понимания процесса. Для дат указать часовой пояс.
- Отсутствующее значение оставить отсутствующим или `null`, не заменять его успешным статусом или нулём.
- Не включать пароли, ключи API, банковские реквизиты, платёжные данные, сканы ID и ссылки с токенами. Для объяснения процесса проверки личности достаточно статусов и правил.

## Что получится после получения примеров

1. Сопоставим реальные вопросы с вашими данными и правилами.
2. Подготовим инструменты чтения для выбранного процесса и адаптируем поведение агента.
3. Для динамического демо подключим агент к модели и обезличенному тестовому источнику данных. Это отдельный шаг после нынешнего сценарного интерфейса.
4. Проверим ответы на согласованных примерах, включая отсутствие данных и передачу специалисту.
5. Покажем, какие случаи агент обработал правильно, где ошибся и какие интеграции ещё нужны для пилота.

Для первого этапа не нужны настоящие ставки, платежи, изменение Buying Power или допуск к рабочим аккаунтам. Сначала проверяем понимание процесса, корректность ответа и границы действий.

**Главное, что нужно вместе с выгрузкой: не только данные, но и ожидаемый ответ или действие сотрудника. Именно это позволит проверить внутреннюю бизнес-логику, которой нет на публичном сайте.**
